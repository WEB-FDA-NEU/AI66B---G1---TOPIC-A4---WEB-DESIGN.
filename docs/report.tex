\section{Project Overview}

Concertly is for concert-goers who want to choose a specific seat, and for organisers who
need to sell those seats without double-booking. A fan opens a concert, picks up to 6 tickets
--- exact numbered seats in a seated zone, or a quantity in a standing zone --- and the tickets are
held for them for 5 minutes while they pay; paying turns the hold into an order with one QR ticket
per seat or standing place. Fans can see their orders and tickets and cancel an order up to 24 hours
before the show. Admins create and edit concerts and their ticket types, see revenue, sales per
concert and orders on a dashboard, and check attendees in at the gate by ticket code or from the
attendee list. The core flow is
\emph{seat map $\to$ 5-minute hold $\to$ checkout $\to$ QR ticket $\to$ gate check-in}.

\textbf{What changed since Milestone 2:} a FastAPI backend on PostgreSQL replaced the mock data
for the concert catalogue, seat selection, holds, checkout, account orders/tickets, login, admin
concert management, the admin dashboard and check-in; zones are now either \emph{seated} or
\emph{standing} (stored in \code{zones.\allowbreak{}booking\_type}); the limit per hold went from 8 to 6 tickets;
an idempotent seed script loads demo data; seat holds, payment and check-in are protected against
concurrent requests; customers can register through the API and log in with their personal
credentials; the API and the site are deployed on Render.
No screens were dropped from the Milestone 2 scope.

\section{System Architecture}

\begin{lstlisting}
Browser: *.html + js/*.js            served by  python -m http.server 5500
   |  js/api.js: fetch('http://localhost:8000/api/reservations',
   |             { Authorization: 'Bearer <token from localStorage>' })
   v
FastAPI (uvicorn :8000): app/main.py -> CORSMiddleware -> routers/reservations.py
   |  Depends(get_db), Depends(get_current_user)  (app/deps.py: verify JWT)
   |  services/reservations.py: SELECT ... FROM seats ... FOR UPDATE
   v
PostgreSQL: users, concerts, zones, seats, reservations, orders, tickets
   ^
   |  background task in main.py: every 30 s releases expired seat holds

Production (Render):
  https://concertly-trang-dat-ve-concert.onrender.com   static site (same files)
        |  fetch  https://concertly.onrender.com/api/...
        v
  https://concertly.onrender.com   Web Service, root backend/  ->  Render PostgreSQL
\end{lstlisting}

The frontend is plain static files served on its own origin (\cpath{http.server} on 5500 or Live
Server locally, a separate Render site in production), so the browser calls the API on another
origin and FastAPI enables \cpath{CORSMiddleware} with origins from \cpath{CORS_ORIGINS} (default
\code{*} locally; the exact frontend origin on Render). FastAPI does not serve the HTML pages; it
only serves uploaded concert posters under \cpath{/uploads}. The API base URL
is \cpath{http://localhost:8000/api} unless \cpath{window.CONCERTLY_API_BASE} is set before
\cpath{js/api.js} is loaded. Every
error is returned as \code{\{"error":\{"code","message",\ldots\}\}}, and write operations run in a
transaction that is retried on deadlock or serialization failure (\cpath{services/txn.py}).

\section{Database Design}

\begin{lstlisting}
users 1 ----< reservations >---- 1 concerts 1 ----< zones 1 ----< seats
  |               | 1                 | 1                           |  reservation_id (FK, null)
  | 1             v 0..1              |                             |
  +----------< orders >---------------+                             |
                 | 1                                                |
                 +----< tickets >-----------------------------------+
                         seat_id (FK), concert_id (FK), checked_in_by -> users

users(id, email, password_hash, full_name, role customer|staff|admin, ...)
concerts(id, title, artist, venue, city, poster_url, starts_at, sale_start_at, sale_end_at,
         status draft|on_sale|sold_out|cancelled|completed, ...)
zones(id, concert_id, name, price, capacity, booking_type seated|standing)   -- ticket types
seats(id, zone_id, row_label, seat_number, status available|held|sold,
      held_until, reservation_id)
      -- for a standing zone each row is one anonymous place; its number is never shown
reservations(id UUID, user_id, concert_id, status active|converted|expired|cancelled, expires_at)
orders(id, order_number, user_id, concert_id, reservation_id, total_amount,
       status, payment_status, refund_status)
tickets(id, ticket_code, order_id, concert_id, seat_id,
        status valid|used|cancelled|refunded, checked_in_at)
\end{lstlisting}
\textbf{Key constraints:} unique index on \code{lower(users.\allowbreak{}email)};
\code{UNIQUE (zone\_id, row\_label, seat\_number)} on seats and \code{UNIQUE (concert\_id, name)} on zones;
\code{orders.\allowbreak{}order\_number} and \code{tickets.\allowbreak{}ticket\_code} UNIQUE; \code{orders.\allowbreak{}reservation\_id} UNIQUE,
so one hold can be paid only once; partial unique index \code{tickets(seat\_id) WHERE status IN ('valid','used')},
so a seat can never have two live tickets; CHECK constraints on every status column, on prices and
capacities ($\geq 0$ / $> 0$), on \code{refund\_amount $\leq$ total\_amount}, and
\code{(status = 'used') = (checked\_in\_at IS NOT NULL)} on tickets;
\code{CHECK (booking\_type IN ('seated','standing'))} on zones; foreign keys as in the diagram
(zones and seats are deleted with their concert). A concert that has orders or reservations
cannot be deleted (409 \code{concert\_has\_bookings}), and a zone's type cannot be changed once it has
tickets or held seats (409 \code{booking\_type\_has\_bookings}). Databases created before the
standing/seated change are upgraded with \cpath{backend/migrations/001_zone_booking_type.sql}
(applied by hand, not at startup; this was done on the Render database on 2026-11-14).

\textbf{Seed data:} \code{python scripts/\allowbreak{}seed.\allowbreak{}py} (data in \cpath{scripts/seed_data.json}) creates
3 users (1 admin, 2 customers), 11 concerts with 33 ticket tiers (7{,}200 places in total) and their
seats (20 seats per row; sold-out tiers get sold seats), and 14 sample orders (\#10001--\#10014):
9 paid, 2 refunded, 1 pending, 1 failed and 1 cancelled before payment, giving a total revenue of
2{,}510 and 16 valid/used tickets on the dashboard. It runs in one transaction under an advisory lock
and only inserts missing rows, so running it again changes nothing. Passwords come from
\cpath{SEED_ADMIN_PASSWORD} / \cpath{SEED_USER_PASSWORD}, or are generated and printed once.
\code{--check} validates the JSON without touching the database; \code{--no-sample-orders} skips orders.
For the demo, only the Admin account above is provided; customers create and use their own accounts.
